# 产品小规模验收协议 v1（提案，2026-11-13）

状态：`proposed`（方案已批准实现，样本尚未冻结）。不是已冻结协议或验收结果。
用户 2026-11-13 已审阅本提案，明确选择“按提案继续实现”；并确认暂无新素材和远端。
核心基线：`79bf438`；现有上游运行器与权重还须单独锁定哈希。

## 1. 目标与边界

回答三个问题：新比赛中能否找到有用的动作片段；展示的轨迹测量有多少可用、
与什么参照吻合；3D 在哪些画面条件下能产生输出。

本轮交付是小规模可行性验收，不是发布认证或通用准确率声明。
三场比赛不足以代表不同联赛、机位和画质；同场不同片段不能当独立比赛。

- 高光先验收“按明确类别找到动作事件”，另记主观有用性，不能把两者混为一项。
- 速度、米制位置只有独立同步测量才能给出真实误差；普通视频人工观察不能提供该真值。
- GSR 结果始终称“相对官方标注的偏差”。本协议不启用原 GSR holdout，也不替代 gates.v2。
- 3D 本轮只报告覆盖率、缺失原因和自洽性，准确度保持 `not_evaluated`。
  无独立 3D 真值、无同条件 2D 基线对照时，不能晋升指标等级。
- 原 `gates.v1.json`、旧评估结果、算法门限和运行器保持原样；改算法属于下一轮开发。

## 3. 样本设计（建议值，审阅后才冻结）

目标三场未用于本项目开发或预实验的比赛，每场四段 30 秒，共十二段、六分钟。
只处理持有本机研究使用权限的材料，不上传视频，不启动付费服务。

每场分两层，独立报告，不能把有意富集事件的样本当自然分布：

1. **事件层两段**：从独立来源的射门事件表选两次不同射门。
   表须在 gbf 输出产生前取得或由盲标者写定。按
   `sha256("gbf-product-v1/" + source_namespace + "/" + match_id + "/" + event_id)`
   升序选前两次，以事件前 10 秒到后 20 秒取窗。
   不按 gbf 分数或“看起来效果好”选；该层只是事件场景测试，不代表全部高光类型。
2. **均匀层两段**：仅按已知的两个半场视频时间边界分成相接的 30 秒候选窗，
   以 `sha256("gbf-product-v1/" + source_namespace + "/" + match_id + "/" + half + "/" + start_frame)` 排序，
   跳过与事件层或已选窗有任何帧重叠的候选，取前两段。
   该层可含停顿、回放和没有事件的片段；没有事件不剔除。

候选窗不能越过原始半场文件边界。事件层不足两次有完整上下文的射门、
事件对齐误差无法确认在 1 秒内、比赛身份不明或同场材料已用于开发时，
该场在推理前判为不合格；按来源清单中比赛哈希顺序补下一场并记录原因。
冻结后不因漏检、缺测、分队失败、结果差而补换样本。
没有可用的独立事件表时停在样本准备阶段，不能临时改为看模型输出挑窗。

三个比赛来源的规范化 ID、文件 SHA256、可用半场起止帧、事件表及其 SHA256、
每个窗的起止帧与原始帧映射进入私有 manifest。实际候选清单仍为空，不能冻结空清单。

## 4. 标注：先看原片，再锁答案，最后看预测

每段完整原片由两名相互独立的标注者查看，可逐帧回放；二者在交标前都不能看 gbf 输出。
记录真实标注者、时间、是否人工、已看过的材料，不能把模型标注写成人工标注。
本次尚未落实标注者；单名标注者或模型单独标注只能给出探索结果。

先列出**全部**可见的目标事件，再标出持续看不清的时间区间及原因。
每个事件记 ID、可接受的类别集合、开始/结束帧、单一代表帧和必要的画面人物位置。
不要求标注者填写任何米制速度或 3D 角度。

| 产品类别 | 可观察的标注定义 |
|---|---|
| duel_tackle | 两名对方球员在球附近直接争抢；代表帧取最近的直接争抢，遮挡不能确认则记不确定 |
| attack_in_box | 可见活球进入/位于禁区并发生一次进攻触球；仅罚球准备或无球站位不算 |
| ball_strike | 能看到或前后帧明确约束的触球及球运动变化；可为传球、射门或解围，不等同“射门” |
| sprint | 可见连续至少 1 秒的明显快速跑动；这只是视觉事件标签，不证明达到某个 km/h |
| closeup_reaction | 球员特写中可见明确手势或反应；普通切镜本身不算 |

同一类别、同一动作主体、连续动作中间不到 1 秒的标记合并为一次事件；
不同主体或不同动作不自动合并。同一物理动作满足多类时只标一次、保留类别集合。
前后不足 1 秒上下文或决定性画面不可见时记为 `uncertain`，不能强填准确触球帧。

两份原始标注分别锁哈希。先在不看预测的情况下对分歧复核形成裁决版，
锁裁决版哈希后才能运行预测。仍无共识的事件/区间继续保留为不确定。
复核日志与原始意见都保留，不能只保存最后答案。
若不确定时间超过某片段帧数的 20%，该片段无高光通过判定，但仍计入失败/覆盖率报告。

## 5. 高光计分与建议通过线

读取最终 `highlights_final.json`，全部 main/candidate 均计入；另报 main 子集，
不得事后按分数调阈值。人工标签和预测一律使用含端点的规范帧号。

允许配对的边须同时满足：时间窗 IoU >= 0.30，人工代表帧落在预测窗内。
先最大化配对数量，再在这些解中最大化 IoU 总和，再最小化代表帧绝对差，
仍相同则按事件 ID、预测 ID 的字典序确定唯一解。配对不使用类别信息，
类别错误在配对后独立计数，不能通过按类别挑配对美化结果。

- TP 是成功的一对一配对数；FN 是全部确定事件中未匹配数。
- FP 是确定可评时间上未匹配的预测数，重复预测同一事件也算 FP。
- 未匹配且预测窗与不确定区间有任何重叠的预测记为 `unscorable`，不直接叫误检。
  主精度按最坏情况把它们并入分母：`TP / (TP + FP + unscorable)`；另报忽略它们的次要版本。
- 召回率 `TP / (TP + FN)`；零分母记 `not_evaluable`，不能写 100%。
- 一个很长的窗口不能靠覆盖代表帧获奖：仍必须满足 IoU。配对只说明找到了事件，
  类型一致率、代表帧偏差、窗口长度和主观有用性另外报告。
- 某段运行失败：这段确定事件全部计 FN，完成覆盖率记失败；不能从合并统计删掉。
  不凭失败段“没有生成预测”认定低误检，应由运行门禁单独阻止通过。

**建议通过线只是工程目标，不是由已有数据推导出的统计保证：**

1. 十二段全部产生运行核验通过的报告，帧对齐和来源哈希检查全部通过；失败不得静默重选。
2. 至少三场比赛、合计至少二十个确定事件；不足记 `insufficient_evidence`，不追看输出后加样本。
3. 两层合并的保守精度、召回率均 >= 4/5（用整数交叉相乘判断，不四舍五入）。
4. 每场有事件时召回率 >= 3/5；每场有预测时保守精度 >= 3/5。
   某场零事件/零预测要原样列出，不能声称该场已经验证了相应比例。
5. 匹配事件中至少 4/5 的代表帧偏差 <= 1 秒。这不是触球帧 ±1 帧的 G14 验收。
6. 不确定区间比例 > 20% 的片段或无法满足盲标流程时，整体不得给出通过结论。

同时逐比赛、逐层、逐类报 TP/FP/FN/unscorable、类别一致率与所有分母；
自然采样层单独报每分钟 FP。不以事件富集层的精度估计自然场景精度。
按比赛重采样 2000 次、种子 0 给出区间并注明仅三场不稳定；
通过线只作小规模点估计筛选，不声称置信下界达标。
两位标注者对“这个片段是否值得保留”的二元意见与理由另存，不参与上述事件通过线。

## 6. 测量和 3D 的结果状态

### 轨迹测量

新视频若没有同步独立位置/速度真值，状态为 `not_evaluated_no_reference`。
可以报告输出覆盖率和拒答原因，不能把重投影自洽或人眼判断当米制真实误差。
将来取得独立真值须另写参考同步、精度、身份配对和通过线，再开新版本，不在本轮补规则。
现有 GSR 评估可作回归，但在 v2/P1/P3/P4 与远端门禁满足前不动原 holdout。
本轮不把原来未测的指标登记成 `measured`。

### 覆盖率（防止只统计“有结果”的项目）

- 高光完成率分母固定为十二段；另报每段系统是否成功、总耗时与失败原因。
- 对每个确定人工事件，按其人工代表帧和主体建评估目标，**包括未检出的事件**。
  无主体框、跟丢、无姿态、无标定、球队未知、方向未知均计缺失。
- 对位置、速度、最近对手分别报“人工事件目标中有可用值的比例”；
  指标不适用（如最近对手没有对手画面）的情况由盲标规则决定并单列，不能由预测决定。
- 3D 分母为人工事件主体在代表帧 ±12 帧内可见的人·帧；窗口截到片段范围。
  人工逐帧画主体框并记录可见性；漏检和未出高光不从分母消失。
  报全部目标覆盖率，以及按主体框高 <80、80–149、>=150 px 分层的覆盖率。
  这些是统计分层，不是本轮新定的上线门限。
- 另报“已有姿态/高光中被接受的比例”作为诊断，不能拿条件分母冒充端到端覆盖。
- 无人工主体/可见性标注时上述覆盖率记 `not_evaluated`；不能用预测框替代漏检分母。

3D 有输出也只称“参考”。沿用现有质量理由计数；重投影误差等只是自洽诊断。
任何 joint 角度准确度、技术优劣判断、3D 优于 2D 的结论均不由本轮认证。

## 7. 冻结、运行、停止和修订

顺序：审阅协议 → 样本/标注者准备 → 原片盲标与裁决锁哈希 → 合成测试与变异检查
→ 锁定核心提交、运行器/权重/输入/标注/参数的哈希 → 项目远端固定提交及服务端时间
→ 才运行独立样本。纯本地记录只能称本地冻结，不能称预注册。

冻结回执包含协议与评估器哈希、全部输入、标注与模型版本、远端提交和推送时间，
每次比较核对实际文件。原材料及逐帧结果放 D 盘私有目录，仓库只存协议和合成测试。
协议内容变更必须新版本，旧结果继续指向旧版本。

先在一段已知 dev 上核对接线、取消、缓存与计时（回归，不算独立验收）。
独立批次一次只跑一段，沿用现有进程树上限和内存守护；可用内存 >=3 GB 才开跑，
<700 MB 停止，至多三次资源不足重试，保留每次日志与失败目录。
预计十二段 CPU 约 24–48 小时，先用 dev 计时更新预算后再开批次。
总活跃模型时间上限 48 小时、单段上限 4 小时；超限保留缓存并停止，不降分辨率或换算法。
关机/取消、解码损坏、哈希不一致、标注泄露、帧映射不一致时停止并登记。
工程修复改变被测输出的，要新版本、新未曝光样本；不得把看过结果后修复的重跑叫首验通过。

## 8. 实现位置、命令和代码约定

保持 Python 3.11/3.12、现有 numpy/scipy/jsonschema/pytest/ruff；不增依赖。
已新增 `src/gbf/evaluate/product.py` 作为独立离线评估命令，
`tests/test_evaluate_product.py` 用可手算的合成样例测试；
仅在 `src/gbf/__main__.py` 注册命令。旧 `gbf.label_eval` 的报告行为不改变。
示例风格：`def match_events(labels: list[dict], predictions: list[dict]) -> dict:`，
运行时输入校验用显式异常，输出 JSON 禁止 NaN，缺测写状态和原因，不写 0。

当前存在、可执行的准备核查命令（PowerShell）：

```powershell
git -C C:\dev\gbf status --short
git -C C:\dev\gbf rev-parse HEAD
git -C C:\dev\gbf remote -v
Set-Location C:\dev\gbf
& .\.venv\Scripts\python.exe -m gbf gate
```

以下计分与预检命令已实现；没有独立材料时返回 `blocked`，不能据此声称真实验收已执行：
其中 `GBF_ACCEPTANCE_ROOT` 由本机环境指定私有验收目录，仓库文档不记录私人数据路径。

```powershell
Set-Location C:\dev\gbf
$acceptanceManifest = Join-Path $env:GBF_ACCEPTANCE_ROOT 'manifest.json'
& .\.venv\Scripts\python.exe -m gbf eval-product --preflight --manifest $acceptanceManifest --out (Join-Path $env:GBF_ACCEPTANCE_ROOT 'preflight')
& .\.venv\Scripts\python.exe -m gbf eval-product --manifest $acceptanceManifest --out (Join-Path $env:GBF_ACCEPTANCE_ROOT 'evaluation')
& .\.venv\Scripts\python.exe -m pytest -q tests/test_evaluate_product.py
& .\.venv\Scripts\python.exe -m ruff check src tests
& .\.venv\Scripts\python.exe -m gbf gate --full
```

`eval-product` 只校验和计分已有输出，不启动模型、不下载、不上传。
预检失败以非零退出，输出明确阻塞项；`not_evaluated` 不能静默变成 `passed`。
模型批次接入现有外部运行器，实际调用参数要在来源齐全后写入锁定清单。

## 9. 审阅后的顺序任务

1. 评估器与合成测试（上述三个源码/测试文件；不改算法）：最大数量配对、乱序不变、重复预测、
   类别错误、零分母、运行失败、缺失片段、不确定帧、错误帧率/哈希和按比赛分组均有手算断言。
   先验证分母包含漏检，再做边界和浮点比较；用变异检查验证分母、IoU、匹配和门禁不能改坏而不报错。
2. 私有 manifest 与标注模板：锁定新比赛来源、完整候选清单、规范帧映射、事件/主体标注及标注者。
   验证无比赛身份重叠、无模型输出参与选样、必填文件和哈希齐全。
3. dev 接线回归：不做新的效果结论，只核对结果读取、缺失计分、资源预算和失败恢复。
4. 推送冻结回执后运行独立批次；生成中文结果，逐项写 `passed/failed/insufficient_evidence/not_evaluated`。
   不把高光通过扩展为速度或 3D 准确度通过。
